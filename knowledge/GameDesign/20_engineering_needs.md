# 20. エンジニアが拡張性・保守性のために必要とする情報（全量）

19章は「どんな要素が出てくるか」。この章は、それに加えて **エンジニアが堅い設計とコードを書くためにデザイナーから貰わないといけない情報の全部** を、エンジニア側の観点で並べたものです。

状態：**決**＝決定済み／**仮**＝デザイナーの仮置きで進めてよい／**未**＝決めてもらう必要あり（設計が変わる）。

---

## 1. 何が「増える」のか（変化の軸）

> 拡張性とは「増えると分かっている物を、既存を触らずに足せること」。だから **何が・どれくらい・誰の手で増えるか** が最初に要る。

| 増える物 | 想定数（仮） | 増やす人 | 足し方の目標 | 状態 |
|---|---|---|---|---|
| アイテム（銃・弾・防具・消耗品・貴重品…） | 300〜600 | プランナー（表） | データ追加のみ | 決 |
| アイテムの特性の種類 | 20〜30 | エンジニア | クラス1つ＋登録1行 | 決 |
| 部品・埋め込み（ルーン等） | 100〜200 | プランナー | データのみ | 決 |
| 能力（魔法・戦技・ガジェット） | 50〜200 | プランナー | データのみ（既存の届け方・効果の組み合わせ） | 仮 |
| 効果の種類（ダメージ・瞬間移動・変身…） | 30〜50 | エンジニア | クラス1つ＋登録1行 | 決 |
| 届け方の種類（弾・領域・光線・呼び出し…） | 8〜12 | エンジニア | クラス1つ＋登録1行 | 決 |
| 条件の種類 | 15〜30 | エンジニア | クラス1つ＋登録1行 | 決 |
| 状態異常 | 30〜60 | プランナー | データのみ | 決 |
| 属性と反応 | 属性 6〜10、反応 15〜30 | プランナー | データのみ（表） | 仮 |
| 敵の種類 | 20〜40 | プランナー＋AI 担当 | 定義＋タスクの木（アセット） | 仮 |
| AI の操作部品 | 20〜30 | エンジニア | クラス1つ | 決 |
| マップ | 3〜6（＋部屋 50〜150） | レベルデザイナー | シーン＋印を置く | 仮 |
| 世界の物の種類（ドア・箱・装置…） | 15〜25 | エンジニア | クラス1つ＋見た目1つ | 決 |
| 仕掛け（これが起きたらあれが起きる） | マップごと数十 | レベルデザイナー | シーン上で組む（コードなし） | 決 |
| ゲームモード | 3〜6 | プランナー | 方針の組み合わせ（新しい方針だけクラス） | 決 |
| クエスト・会話 | 50〜200 | プランナー | データのみ | 仮 |
| 目標の種類 | 10〜15 | エンジニア | クラス1つ＋登録1行 | 決 |
| 拠点施設・レシピ・商人 | 各 10〜100 | プランナー | データのみ | 決 |
| 画面・HUD 要素 | 20＋20 | UI 担当 | 画面1枚＝View＋Presenter | 決 |
| 演出の合図 | 数百 | 演出担当 | データのみ | 決 |
| 能力値の種類 | 60〜120 | プランナー | データのみ | 決 |

**「データだけで足せる」と「コードが要る」の境界を全員で共有すること**が保守性の核。上の表がその約束。

## 2. 壊れてはいけない決まり（不変条件）

> 保守性とは「どこを直しても、守るべき決まりが破れないこと」。決まりを先に言葉にしておけば、検査（テスト）にできる。

| # | 決まり | 状態 |
|---|---|---|
| I1 | アイテムは**必ずちょうど1か所**にある（複製しない・消えない）。移動は「検証→実行」の1単位で、失敗したら何も変わらない | 決 |
| I2 | 収納は自分自身の中に入らない。入れ子の深さに上限 | 決 |
| I3 | 能力値の補正・タグ・能力・発動効果には**必ず出所**があり、出所が消えれば一緒に消える（付けっぱなしにならない） | 決 |
| I4 | 同じシード・同じ入力なら同じ結果（ルート・敵配置・AI の抽選）。演出の乱数はゲーム結果に影響しない | 仮 |
| I5 | 敵とプレイヤーは同じルールで動く（同じ武器・同じ能力・同じダメージ計算）。差はデータと「頭」だけ | 決 |
| I6 | ルール側（計算・判定）は画面部品に依存しない。画面が無くても動く（検査できる） | 決 |
| I7 | セーブには定義の ID と状態だけを書く。ID は変更しない（変えるなら読み替え表） | 決 |
| I8 | 1つのレイドは1つのモードに属し、方針は途中で変わらない。モード間でプロファイルは混ざらない | 決 |
| I9 | 時間に関わる処理はすべてゲーム内時計で進む（実時間待ち禁止）。ポーズ中はルール側が1歩も進まない | 決 |
| I10 | ダメージは必ず計算の流れを通る（HP を直接書き換えない）。結果には理由が残る | 決 |
| I11 | できない操作には**必ず理由**が返る（UI が「なぜ出来ないか」を出せる） | 決 |
| I12 | 死亡・破棄したアクターを参照し続けない（ID で引き直す） | 決 |
| I13 | 大量に出る物（弾・音・演出・領域）は上限数を持ち、超えたら古い物から捨てる | 仮 |
| I14 | レイド中にプロファイルを書き換えない（精算で一度に反映）。強制終了しても中途半端な状態が残らない | 仮 |

**デザイナーに決めてほしいこと**：I4 をどこまで厳密にするか（リプレイ・日替わりシードをやるなら厳密、やらないなら緩くてよい）。→ 未

## 3. 同時に起きたときの順番（優先・タイミングの決まり）

> ここが曖昧だと、実装者ごとに違う順番になり、後から直せなくなる。

| 場面 | 決めること | 仮置き | 状態 |
|---|---|---|---|
| 相打ち | 同じ瞬間に両者が致命傷 → 両方死ぬか、先に撃った方が勝つか | 両方死ぬ | 仮 |
| 死亡と脱出が同時 | 脱出完了の瞬間に致命傷 | 死亡優先 | 未 |
| 死亡後の効果 | 死んだ者が撃った弾・置いた罠・継続ダメージは有効か、キルは誰の物か | 有効。付与者の物 | 仮 |
| 状態異常の同時付与 | 付与順、打ち消し合い（炎上と濡れ） | 反応表で決める | 仮 |
| 回復とダメージが同フレーム | どちらを先に | ダメージ→回復 | 仮 |
| 防御の重なり | 盾＋ガード＋防具＋結界の適用順 | 外側から：結界→盾/ガード→防具→耐性 | 仮 |
| 補正の適用順 | 加算→加算倍率（合算）→乗算→上書き→上下限 | 05章 | 決 |
| 入力の同時 | 回避と射撃とリロードが同フレーム | 優先度表（03章） | 仮 |
| 行動の割り込み | 何が何を中断できるか | 行動ごとの優先度と中断可能区間 | 仮（表が必要：未） |
| 能力の冷却と持ち替え | 持ち替えで冷却は進むか・消えるか | 進む | 仮 |
| 1フレーム内の処理順 | 入力→頭→行動→シミュレーション→後処理→表示 | 設計どおり | 決 |
| 弾と扉 | 開閉途中の扉に弾が当たる | 閉じている扱い | 仮 |
| 反応の連鎖 | 反応が反応を呼ぶ（爆発→着火→爆発） | 1フレーム1段、上限回数あり | 仮 |
| イベントの配信順 | 同じ出来事を複数の機能が見る順 | 順序に依存しない作りにする（依存するなら明示） | 決 |

**デザイナーに作ってほしい物**：「行動の割り込み表」（行＝いまの行動、列＝来た行動、マス＝中断する/待つ/無視）。能力・戦技が増えるほど必須。→ 未

## 4. 寿命と持ち主（いつ生まれ、いつ消え、誰が持つか）

| 範囲 | 中身 | 始まり〜終わり |
|---|---|---|
| アプリ | 時計・設定・定義の目録・セーブ・画面管理・音 | 起動〜終了 |
| プロファイル | 共有データ（設定以外の図鑑・実績） | スロット選択〜切替 |
| モード | スタッシュ・通貨・商人・拠点・クエスト・育成・世界の記憶・仲間 | モード選択〜切替 |
| 拠点滞在 | 売買・クラフト・改造の画面と進行役 | 拠点に入る〜出撃 |
| レイド | アクター・弾・世界の物・領域・合図・環境・戦果 | 出撃〜精算 |
| ラン（ローグライト型） | 層をまたぐ強化・持ち物 | ラン開始〜死亡/踏破 |
| アクター | 部品・状態異常・能力の冷却・記憶 | 出現〜破棄 |
| 行動 | 区間の進行・中断 | 開始〜完了/中断 |

**決めること**：ラン（複数層）の間に何を持ち越すか／仲間は死んだら永久に失うか／呼び出した物は層をまたぐか。→ 未

## 8. うまくいかなかったときの振る舞い

| 場面 | 決めること | 仮置き |
|---|---|---|
| アセットのロード失敗 | 仮の見た目で続行か、止めるか | 仮の見た目＋ログ |

## 10. 「分かるように見せる」ための要求

ルール側は、起きたことを**理由つきの出来事**として必ず出す。画面・音・統計・クエスト・チュートリアルはそれを聞くだけ。

| 出来事の例 | 聞く側 |
|---|---|
| 命中（部位・貫通/非貫通・跳弾・反応） | ヒットマーカー、音、統計、クエスト、発動効果 |
| 防御成功（ガード/パリィ/反射/回避） | 演出、時間減速、ゲージ |
| 能力の発動・中断・冷却完了 | HUD、音 |
| 状態異常の付与・解除 | HUD、ヒント |
| 操作の失敗と理由 | HUD のメッセージ |
| 気づきの段階変化 | HUD、音楽、分隊 |
| 世界の変化（扉・壁・照明・電源） | 経路、視線、音、地図 |
| 進行（クエスト・レベル・解放） | 通知、セーブ |

**決めること**：HUD にどこまで情報を出すか（敵の HP・気づきゲージ・ダメージ数字・冷却時間）。出す情報が多いほど「出来事」に載せる中身が増える。→ 未

## 12. 現行コードから設計へ移るための順番（保守の観点）

一度に作り直さず、動く状態を保ったまま置き換える。

| 段 | やること | 外す現行コード |
|---|---|---|
| 0 | 不具合の修正（01章 B1〜B25 のうち致命的な物）、名前空間と asmdef の整理 | — |
| 1 | 基盤：時計・イベント・乱数・System 実行器・依存の配線 | `GameMain` / `GameStatus` / `GameEventBus` |
| 2 | 能力値の統合 | `Stats` 系と `StatController` 系の2系統 |
| 3 | アクターの部品化、入力→コマンド→行動 | `PlayerController` / `InputSystem` の直結部分 |
| 4 | ダメージの流れ、部位HP、状態異常 | `IDamagable` / `Buff` 系 |
| 5 | アイテムの特性化、インベントリ操作、UI 接続 | `ItemData` 継承 / `IItemRuntimeData` |
| 6 | 武器ロジックの分離（銃の部品化）、弾道（貫通・跳弾） | `AGunBase` と5銃種 / `GunService` |
| 7 | 効果・条件の共通語彙、能力 | — |
| 8 | 知覚・AI | HTN の実行部分 |
